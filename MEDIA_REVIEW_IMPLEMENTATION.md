# Инструкция по внедрению защищённой галереи «Было / Стало»

Документ описывает внедрение служебной галереи завершённых генераций, личной
истории пользователя, защищённой выдачи изображений и удаления пар медиафайлов
в текущий проект `ritual-retouch`.

## 1. Что важно учесть до начала

Текущая версия проекта:

- хранит файлы в `uploads/`;
- раздаёт их публично через `/uploads/`;
- сохраняет URL или имена файлов в `generations.source_file_id` и
  `generations.result_file_id`;
- связывает загруженный файл с владельцем через таблицу `uploads`;
- запускает генерацию через `src/web/generateRoute.ts`;
- регистрирует HTTP-маршруты в `src/webServer.ts`.

Нельзя сначала удалить публичный маршрут `/uploads/`, а потом переводить
остальные части приложения на новые URL. Сначала должны быть обновлены backend,
frontend, уведомления администратора и интеграция с KIE.ai.

Перед изменениями:

```bash
git status --short
yarn install --frozen-lockfile
yarn build
```

Существующие незакоммиченные изменения в `src/services/kieai.ts` нужно сохранить
и проверить отдельно. Не смешивайте их с внедрением галереи в один коммит без
необходимости.

## 2. Конфигурация и секреты

Добавьте в `.env.example` и production `.env`:

```dotenv
MEDIA_REVIEWER_EMAIL=reviewer@example.com
MEDIA_URL_SECRET=replace-with-a-long-random-secret
```

Требования:

- в production `MEDIA_REVIEWER_EMAIL` должен задаваться явно;
- email нормализуется через `trim().toLowerCase()`;
- `MEDIA_URL_SECRET` должен быть отдельным секретом, не равным `BOT_TOKEN`;
- длина секрета должна быть не менее 32 случайных байт;
- секрет нельзя выводить в логи и нельзя передавать во frontend;
- при отсутствии секрета production должен завершать запуск, а не молча
  использовать `BOT_TOKEN`.

Сгенерировать значение можно, например, так:

```bash
openssl rand -hex 32
```

В `src/config.ts` добавьте настройки с проверкой окружения. Для dev можно
использовать отдельный локальный секрет, но не production-секрет.

## 3. Изменение схемы базы данных

Текущая инициализация использует `CREATE TABLE IF NOT EXISTS`, поэтому изменение
определения таблицы `accounts` не обновит уже существующую базу. Добавьте явную
миграцию или идемпотентный `ALTER TABLE` до запуска новых маршрутов:

```sql
ALTER TABLE accounts
ADD COLUMN IF NOT EXISTS media_reviewer BOOLEAN NOT NULL DEFAULT FALSE;

CREATE INDEX IF NOT EXISTS idx_generations_account_completed
ON generations (account_id, completed_at DESC)
WHERE status = 'completed';

CREATE INDEX IF NOT EXISTS idx_uploads_account_filename
ON uploads (account_id, filename);
```

Предпочтительный вариант для текущего проекта — добавить функцию миграции в
`src/database.ts`, вызываемую из `initDb()`. Все SQL-запросы должны оставаться
параметризованными.

После добавления колонки назначайте проверяющего только при одновременном
выполнении условий:

```sql
email_verified = TRUE
AND lower(trim(primary_email)) = lower(trim(MEDIA_REVIEWER_EMAIL))
```

Проверка email должна выполняться при каждом запросе к служебному API. Одного
флага `media_reviewer` недостаточно: после смены email или конфигурации доступ
должен автоматически закрываться.

## 4. Внутренняя модель файлов

Зафиксируйте единый формат имён:

```text
YYYYMMDD_HHMMSS_<uuid>_src.jpg
YYYYMMDD_HHMMSS_<uuid>_result.jpg
```

В базе храните только безопасное имя файла, без `/uploads/`, полного пути и URL.
Входное имя файла от клиента никогда не используйте как имя на диске.

Для каждого входящего файла необходимо проверить:

1. имя создано сервером через `crypto.randomUUID()`;
2. расширение разрешено политикой приложения;
3. файл записан внутри `UPLOADS_DIR`;
4. запись в `uploads` принадлежит текущему `account_id`;
5. при запуске генерации файл существует и не является директорией;
6. путь после `realpath` остаётся внутри `UPLOADS_DIR`.

Проверка только через `path.basename()` недостаточна, если в каталоге могут
появиться символические ссылки.

## 5. Подписанные URL изображений

Создайте `src/web/mediaRoute.ts` с двумя функциями:

- `createMediaUrl(filename, ttlSeconds)` для формирования ссылки;
- защищённый `GET /media/:filename` для выдачи файла.

Подпись должна рассчитываться по канонической строке:

```text
filename + "\n" + expires
```

Используйте HMAC-SHA256 и hex или base64url в одном фиксированном формате.

Правила маршрута:

- разрешены только `jpg`, `jpeg`, `png`, `webp`;
- `filename` должен быть одним basename без `/`, `\\`, `..` и NUL-байтов;
- `expires` должен быть целым Unix timestamp в секундах;
- стандартный TTL — 15 минут;
- максимальный срок вперёд — 1 час;
- просроченная подпись отклоняется;
- длина подписи проверяется до `timingSafeEqual`;
- путь проверяется через `realpath` и containment внутри `UPLOADS_DIR`;
- неизвестный или отсутствующий файл возвращает `404`;
- неверная подпись возвращает `403` без подробностей.

Заголовки ответа:

```text
Cache-Control: private, no-store
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

Не записывайте полные подписанные URL в логи. Подписанный URL является bearer-
токеном: любой, кто его получил, может читать изображение до истечения срока.

## 6. Порядок изменения backend

### 6.1. Загрузка

В `src/web/uploadRoute.ts` после сохранения файла возвращайте подписанный URL
через helper из `mediaRoute.ts`. Запись в `uploads` должна завершиться успешно
до ответа клиенту.

Если запись в БД завершилась ошибкой, удалите уже созданный файл. Если поток
загрузки оборван или превышен лимит, также удалите частичный файл.

### 6.2. Проверка владения при генерации

В `src/database.ts` добавьте функцию вида:

```text
findUploadForAccount(accountId, filename)
```

В `src/web/generateRoute.ts`:

1. принимайте только ожидаемый формат upload URL или filename;
2. извлекайте basename;
3. проверяйте запись в `uploads` для текущего пользователя;
4. проверяйте существование файла;
5. только после этого резервируйте генерацию и создавайте запись в `generations`.

Сейчас генерация извлекает basename и открывает файл без проверки владельца,
поэтому этот пункт является обязательным исправлением безопасности.

### 6.3. Существующие ответы API

Обновите:

- `GET /api/web/generation/:id/status`;
- `GET /api/web/generations`;
- ответы upload и новых generation endpoint.

Каждый ответ должен строить URL заново из имени файла и текущего срока действия.
Не храните подписанные URL в БД: после истечения TTL их нельзя восстановить.

Для старых записей, где в поле лежит `/uploads/file.jpg`, добавьте временный
normalizer, который безопасно извлекает basename и отклоняет всё остальное.
После миграции данных можно удалить обратную совместимость.

### 6.4. KIE.ai и уведомления

Текущая реализация KIE.ai загружает локальный файл через base64. Это допустимо и
не требует публичного URL. Если всё же передаёте KIE.ai подписанную ссылку,
используйте отдельный короткий TTL и учитывайте, что внешний сервис получает
доступ к изображению до истечения ссылки.

В `notifyAdminWebGeneration` замените публичные `/uploads/...` ссылки на
подписанные URL. Не отправляйте в Telegram ссылки без срока действия.

### 6.5. Доступ проверяющего

В `src/web/auth.ts` добавьте helper `requireMediaReviewer(req, reply)`.
Он должен требовать одновременно:

1. валидную Bearer-сессию;
2. существующего пользователя;
3. подтверждённый email;
4. `media_reviewer = true`;
5. точное совпадение нормализованного email с `MEDIA_REVIEWER_EMAIL`.

Обычный пользователь не должен получать поля `email`, Telegram ID или username
в пользовательском endpoint галереи.

## 7. API галереи

Создайте `src/web/reviewRoute.ts` и зарегистрируйте его в `src/webServer.ts`.

### Пользовательский endpoint

```text
GET /api/web/review-generations
Authorization: Bearer <session>
```

Возвращайте только записи текущего аккаунта, где:

```sql
status = 'completed'
AND source_file_id IS NOT NULL
AND result_file_id IS NOT NULL
```

Для каждого файла генерируйте свежий подписанный URL. Используйте пагинацию,
например `limit` не более 50 и `cursor` или `page`. Не возвращайте все записи
без ограничения.

### Служебный endpoint

```text
GET /api/internal/generations?page=0&limit=50
Authorization: Bearer <session>
```

Сканирование диска должно:

- использовать `readdir` с `withFileTypes`;
- принимать только строгий шаблон имён;
- не следовать за symlink за пределы `UPLOADS_DIR`;
- сопоставлять только пары с одинаковым UUID-префиксом;
- сортировать по времени из имени или `mtime`;
- ограничивать `limit` и максимальный размер ответа;
- дополнять данные из БД отдельным параметризованным запросом.

Отсутствие записи в БД не должно приводить к ошибке всего ответа: возвращайте
пару с `generation: null` и явно отмечайте orphan-файл.

Каждый просмотр служебного endpoint логируйте с ID проверяющего и количеством
возвращённых элементов. Не логируйте prompt и подписанные URL.

### Удаление пары

```text
DELETE /api/internal/media-pairs/:sourceFilename
Authorization: Bearer <session>
```

Порядок операции:

1. повторно проверить права проверяющего;
2. проверить строгий формат `sourceFilename`;
3. вычислить имя result-файла только сервером;
4. проверить оба пути через `realpath` и containment;
5. атомарно переименовать существующие файлы в quarantine;
6. в транзакции обновить связанную генерацию:
   `status = 'deleted'`, `source_file_id = NULL`, `result_file_id = NULL`;
7. удалить quarantine-файлы после успешного commit;
8. вернуть `204` или идемпотентный успешный ответ, если файлы уже удалены.

Если второй файл или обновление БД не удалось, не выдавайте видимость успешного
удаления. Оставьте quarantine для повторной обработки и запишите ошибку.

## 8. Изменения frontend

Добавьте:

- `frontend/src/pages/review-gallery.ts`;
- `frontend/src/components/image-preview.ts`;
- API-функции и типы в `frontend/src/api.ts` и `frontend/src/types.ts`;
- страницу и навигацию в `frontend/index.html` и `frontend/src/main.ts`.

В `main.ts` добавьте страницу в список маршрутов только для авторизованного
пользователя. Прямой вход на `/app/internal/gallery` должен показывать обычную
форму авторизации, а не раскрывать наличие служебной страницы.

Кнопку служебного режима показывайте по `can_review_media`, но серверная проверка
остаётся обязательной. Нельзя считать frontend-флаг механизмом авторизации.

Общий preview должен:

- закрываться кнопкой, Escape и кликом по backdrop;
- сохранять предыдущий focus и возвращать его после закрытия;
- блокировать прокрутку только на время открытия;
- корректно восстанавливать состояние после ошибки загрузки изображения;
- не создавать повторные обработчики при каждом переходе между страницами.

Истёкшие URL должны обрабатываться понятным сообщением и повторной загрузкой
страницы галереи, а не бесконечным циклом запросов.

## 9. Регистрация маршрутов и заголовки

В `src/webServer.ts`:

1. зарегистрируйте `mediaRoute` и `reviewRoute` до SPA fallback;
2. не подключайте `@fastify/static` для `/uploads/` после миграции;
3. оставьте `uploads/` доступным только через `/media/:filename`;
4. для `/app/internal/gallery` установите:
   `X-Robots-Tag: noindex, nofollow, noarchive`;
5. добавьте `Cache-Control: private, no-store` для HTML служебной страницы;
6. проверьте, что SPA fallback не перехватывает API-ошибки.

## 10. Тестирование

### Backend

Минимальный набор проверок:

- пользователь A не видит генерации пользователя B;
- пользователь A не может запустить генерацию с upload пользователя B;
- неподтверждённый email не получает reviewer-доступ;
- email с другим регистром работает корректно;
- обычный пользователь получает `403` от `/api/internal/generations`;
- просроченный URL возвращает ошибку;
- URL с TTL больше часа отклоняется;
- изменённый `filename`, `expires` или `sig` отклоняется;
- `../`, slash, backslash и symlink не позволяют выйти из `uploads/`;
- разрешённые форматы выдаются с правильным Content-Type;
- удаление одной пары не затрагивает другую;
- повторное удаление не вызывает ошибку состояния;
- ошибка удаления не очищает ссылки в БД преждевременно;
- orphan-файлы отображаются отдельно и не ломают весь список.

### Frontend

Проверьте вручную в desktop и mobile:

- навигацию авторизованного и неавторизованного пользователя;
- открытие страницы прямым URL;
- обновление истёкших ссылок;
- fullscreen preview и возврат фокуса;
- Escape и блокировку прокрутки;
- отсутствие показа reviewer-полей обычному пользователю;
- подтверждение удаления и обновление списка после удаления.

Команды перед релизом:

```bash
yarn build
yarn build:frontend
docker compose -f docker-compose.dev.yml build bot
docker compose -f docker-compose.dev.yml up -d bot
docker compose -f docker-compose.dev.yml logs --tail=200 bot
```

## 11. Порядок релиза

### Этап A: подготовка

1. Сделать резервную копию PostgreSQL и volume `uploads_data`.
2. Добавить новые переменные окружения.
3. Добавить миграцию схемы без удаления `/uploads/`.
4. Развернуть backend с генерацией подписанных URL параллельно со старыми URL.

### Этап B: переключение клиентов

1. Перевести upload и все ответы API на `/media/...`.
2. Обновить frontend и уведомления администратора.
3. Проверить новые и старые записи генераций.
4. Проверить, что KIE.ai получает источник и завершает генерацию.

### Этап C: закрытие публичного доступа

1. Убедиться, что поиск по frontend/backend больше не содержит `/uploads/` как
   публичного URL.
2. Проверить старые изображения через новую выдачу.
3. Удалить регистрацию `@fastify/static` для `/uploads/`.
4. Пересобрать и перезапустить контейнер.
5. Проверить прямой запрос к `/uploads/<file>`: он должен возвращать `404`.

Перезапуск production согласно правилам проекта:

```bash
sudo docker compose build bot && sudo docker compose up -d bot
```

## 12. Откат

Если после переключения перестали открываться изображения или генерации:

1. не удаляйте volume `uploads_data`;
2. верните предыдущий образ контейнера;
3. временно восстановите `/uploads/` только для диагностики;
4. не откатывайте миграцию `media_reviewer`, если она уже применена;
5. после исправления повторите переключение клиентов до отключения публичного
   маршрута.

Перед отключением старого маршрута нужно иметь отдельный backup БД и файлового
volume. Физическое удаление media-пар необратимо и не должно быть частью первого
релиза новой галереи.

## 13. Критерии готовности

Функционал считается готовым, если:

- `yarn build` и frontend build проходят;
- существующие пользователи видят свои завершённые генерации;
- пользователь не может получить чужое изображение или использовать чужой upload;
- reviewer API закрыт всеми требуемыми проверками;
- публичный `/uploads/` отключён и не используется приложением;
- подписанные URL имеют ограниченный TTL и правильные заголовки;
- удаление пары не оставляет неконтролируемого частичного состояния;
- есть backup и проверенный план отката;
- проверены старые записи, orphan-файлы и пустой каталог `uploads/`.
